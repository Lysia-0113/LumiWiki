# 复杂后台 Skill 的设计约束

唯一主要交付是普通用户能完成核心任务的简短图文指南。先明确受众、权限、3至5个重要用户目标（小范围可更少）与可用模块标准，再收集最小必要页面证据；复杂后台策略是按需参考，不是全部任务的强制执行清单。采购后台、预约和工单是检验可迁移机制的实例，不能用实例数量代替通用性证明。

| 通用机制   | 必须保持的约束                                                   | 具体业务放在哪里                           |
| ---------- | ---------------------------------------------------------------- | ------------------------------------------ |
| 观察协议   | 真实层级、活动区域、行归属和字段状态；过期ref不能继续使用        | 页面本身；特殊组件可由适配层扩展           |
| 任务契约   | 角色、目标、前置状态、关键步骤、结果和恢复方式明确               | Wiki与本次任务，不写死在引擎               |
| 定位与条件 | 按字段标签或已观察控件定位；按唯一键与列核对同一记录             | 字段名、状态值、记录键来自业务材料和页面   |
| 过程证据   | 检查点有顺序且截图可追溯；模型不能提交passed                     | 业务选择哪些步骤重要，宿主检查它们是否执行 |
| 跨页结果   | 各页结果分别核验与截图，覆盖全部条件；新写请求撤销当前场景的结果 | 页面分组随任务变化                         |
| 生命周期   | 有预算、有取消、有有限续跑；全场景受阻后停止业务操作             | 缺账号、数据或能力时明确受阻               |

默认 `profile=general`，一般后台指南也不要求机械的中间 checkpoints，只核验支撑用户操作的关键条件。只有复杂业务端到端核验或明确要求深度业务验收时才显式选择 `profile=admin`，保留成功场景至少2个检查点、其他分支至少1个的严格底线；已规划检查点均按顺序核验和截图。工具次数、检查点数量和凑齐 success/empty/error/permission 不是指南质量指标。是否选中了真正影响任务成败的步骤、业务条件是否充分，仍需复核。

文档交付优先：每个满足门禁的模块尽早保存为独立可用的简短图文说明，遇阻保留成果与明确限制。不为生成指南冒险修改业务数据；只用授权账号与数据，不重复创建或提交。没有安全提交条件时可选择已观察的查询或填写准备为独立目标，明确“未实际提交，业务结果未验证”；不能把表单、toast 或模型宣告 passed 当成业务完成。已锁定而无法完成的提交场景标受阻，不降低检查条件。

核心运行时使用标准可访问性角色、表单属性、表格列与HTTP方法，不识别采购单号、具体菜单名、业务状态或接口路径。这些内容保留在实例与测试实现中。新增系统时应替换任务契约和适配能力，复用运行机制。

## 验证思路

用反例检查约束：同名按钮是否会操作错行、成功提示能否冒充业务完成、两行数据会不会被混用、跨页结果是否遗漏、截图是否属于对应证据、取消后是否还继续操作。它们验证同一套机制，不构成全量页面清单。

自动化浏览器回归涵盖代表性后台流程；真实模型验收还检查实际服务端变更、刷新后查询顺序、结果证据及导出图片。两类证据分别保留，不能只根据一份绿色报告声称所有后台都适用。

## 当前边界

结果等级是UI检查，任务契约和指南均为待复核草稿。浏览器观察到的同站写请求计数是保守失效机制；它不能证明数据库事务一致性，也不覆盖外部并发写或WebSocket状态变化。可信后端验证、SSO和自动数据准备仍属于系统适配能力。

代表性采购后台有独立HTTP后端，但仍是本地验收实现。它不代表已验收任意第三方ERP或全部组件库。后续验证应优先选择另一套真实目标后台，检查相同约束是否仍然成立；不把业务特例补进核心。
