# 执行参考（按需查阅）

主文定义交付标准；这里说明当前工具的参数与门禁，不是每次开始前的必读清单。开发者测试命令和结果不属于目标系统知识或当次操作指令。

## 目标、范围与 profile

先明确受众和最重要的3至5个用户目标（小范围可更少），以读者能独立完成核心任务的图文模块为标准，再找支撑说明的最小必要证据。模块不是菜单目录，工具次数、检查点数量和四类场景覆盖率都不是交付质量指标。

默认 `profile=general`，宿主在省略 profile 时也使用 general；可不设中间 checkpoints，仍须核验前置状态、实际目标和归档结果截图。只有复杂业务端到端核验或用户明确要求深度业务验收时，显式选择 `profile=admin`：成功场景至少2个中间 checkpoints，其他分支至少1个。已选择的检查点在两个 profile 中都必须按顺序核验、截图，再继续；admin 不替代授权，也不是一般后台指南的默认模式。

没有安全提交条件时，将已观察的查询、定位或填写准备定义为独立目标，outcomes 只断言这些真实状态。`goal` 和 `coverageReason` 写清范围；指南明确“未实际提交，业务结果未验证”，不把表单就绪说成创建、审批或结算成功。未打开的表单不能凭 Wiki 猜字段。已锁定的提交目标无法执行时应 block，而不是改成弱断言；同模块有其他已核验场景时仍可保存有用说明，全部受阻时只跳过并说明原因。

## 契约参数

工具 schema 定义参数，机器可读副本在 `schemas/task-plan.schema.json`。计划含1至8个模块，每模块1至4个场景；这是容量边界，不是数量目标。模块是用户任务，场景是相关初始状态下的路径，不要求凑齐 success、empty、error、permission；`kind` 描述该目标路径，不代表宿主认证业务成功。

- `audience`：角色和权限范围。
- `coverageReason`：为何选择这些路径、实际验证范围和缺口。
- `goal`：用户要实现的结果，与实际可核验范围一致。
- `setup`：已有测试状态、人工准备或宿主已注册的适配能力。
- `preconditions` / `outcomes`：可执行的只读 UI 断言，覆盖关键条件即可。
- `checkpoints`：需要留证的关键中间状态；general 可省略，admin 保持上述数量与顺序门禁。
- `cleanup`：恢复办法。写出计划不代表已执行清理；说明实际情况，不擅自清理业务数据。

锁定前通过 `browser_observe` / `browser_inspect` 看清相关区域，用 `browser_navigate` 探查所需任务页面，再选择真实存在的结果条件。它只接受导航区控件、tab 或同站链接，拒绝表单与非导航业务按钮。契约前 `browser_act` 允许导航、返回、滚动、悬浮、展开和收起；通用点击与填写在契约后。探路受登录或弹窗阻碍时记录所需准备，不凭 Wiki 猜验收文本。

## 定位与断言

定位器支持 `{role,name}` 精确可访问名称、`{text}` 精确文本、`{testId}`、`{css}` 和表单的 `{label:字段标签}`。不执行模型提供的 JS、SQL、HTTP 请求或 shell。未观察字段时不猜 radio、combobox 等角色；宿主会拒绝未观察到的字段控件角色。优先用 label 跨控件类型定位。

断言支持 `visible`、`hidden`、`enabled`、`disabled`、`checked`、`unchecked`、`text_contains`、`text_equals`、`value_equals`、`selected_label_equals`、`row_fields`、`count`。

- 文本填 `texts` 数组；contains 要同一对象包含全部字段，equals 修剪两端空白后等于唯一的 texts 值。金额、状态等用精确比较，不能用包含“0”判定零余额。
- `value_equals` 检查表单当前值，texts 只有一个值；`selected_label_equals` 比较当前选中项的可见标签，texts 为所需标签列表。输入框不能用 text_equals，存在选项不等于选中。
- 数量填 `count`。正向对象须唯一且可见；不存在或零数量须指定唯一可见的 `scope`，防止页面未加载假通过。
- `row_fields` 指定表格、`rowKey`（column/value）和 `fields`（各 column/value），唯一匹配行的指定列必须精确相等。不猜未来整行的完整名称，不混用其他行字段。

实际提交后，检查同一对象的唯一标记、关键字段和状态，不能只看全页“成功”或一次点击。若选择错误路径，应同时核对错误和不应发生的变化。UI 条件成立不证明持久化、结算、并发一致性或后端权限隔离；无法证明的事实标为未验证，需要可信业务适配器时明确说明。

## 执行与证据

`定义可用模块 → 必要观察与导航 → plan → prepare → begin → 关键操作（可选 checkpoint）→ verify → 截图/标注 → 立即 document → publish`

1. `quick_start_prepare(moduleId, scenarioId)` 切换准备阶段，封存前一场景证据；只使用已授权的账号、数据和浏览器操作。种子、SSO 或后端检查只有宿主注册后才能使用，不能编造接口。`quick_start_begin` 实际核验前置状态；失败则安全修复或 `quick_start_block`，不跳过。
2. 观察 → 使用最新 ref 操作 → 重新观察。等待明确异步条件用 `browser_wait`，不猜加载中或禁用状态。general 只需核验支撑内容的关键操作；已计划的检查点用 `quick_start_checkpoint` 顺序检查并截图，不因追求简短而跳过。
3. `quick_start_verify` 核验实际目标。状态是 `pending / active / verified / blocked`，结果由宿主生成；模型不能提交 `passed:true`。verified 只表示指定 UI 条件成立，不把它改写成未发生的业务成功。
4. 单页结果可省略参数；跨页结果传 `outcomeIds` 分组，每组通过后先 `browser_screenshot` 再导航。默认全量检查未通过时，可用返回的 `availableOutcomeIds` 选择本页条件，不要求多页同时显示。全部组都有证据才完成；只通过一组不能称全部完成。
5. 截图返回该图专属 ref 并刷新页面 ref。`image_annotate` 用截图冻结坐标画框，文案解释 legend 编号。原图保留；只有原图已归属于对应检查点或结果组，派生图才继承证据资格。
6. 每组截图后可以导航或筛选到下一组。新的同站非 GET/HEAD/OPTIONS 请求撤销当前场景的结果组，须重新核验；POST 查询也会保守失效。这是浏览器观察到的请求计数，不是数据库事务版本。失败后先分析真实状态，不盲目重复提交；切换场景前先保存每组结果截图再 prepare。

## 保存、受阻与汇总

`quick_start_status` 返回宿主状态，`readyModules` 列出可保存模块及合法图片 ID。模块内场景都已核验或明确受阻后，立即 `document_write(moduleId, ...)` 保存完整可用模块，再继续下一模块；至少一个场景真实核验且有归档图才能写文档。用户只选本模块关键图片展示，全部已计划检查点及结果组证据仍需归档。

文档写适用角色、必要准备、入口、关键填写、确认结果的方法及真正影响操作的限制，通常3至6步、少量关键图。未提交部分明确标为未验证；已核验的定位或准备流程仍可有用，不伪装成完成提交。引用 `page` 用本会话观察过的完整 URL；`doc` 用 `wiki_read.citation` 或全文目录的 pageId；图片用当前会话工具创建且获准用于本模块的 ID。宿主继续检查项目、会话、模块、截图与引用归属。

账号、权限、测试数据、验证码或第三方入口不可达时，block 写具体原因，不据此说系统没有功能。预算不足也先保存已经满足门禁的模块与证据、列明剩余缺口；不为生成指南冒险修改业务数据。继续任务时保留原计划、文档与已核验状态，不重复创建或提交。block 和跳过不计为成功。

`quick_start_publish` 为每个模块提供绑定文档或具体跳过原因。宿主复核证据和产物归属，完整执行细节留在 JSON，用户导出显示必要限制。未通过门禁时说明未完成，不声称已经发布。未汇总且预算允许时宿主可有限续跑；取消、运行错误或全场景受阻时不自动继续，不靠续跑降低门禁。

指南之后由宿主自动整理 QA，失败不影响指南；整理后是否可复用由宿主 QA 准入策略决定，本 Skill 不规定人工审核或直答准入。迁移系统时重新观察和定义角色、目标及条件；需要可靠自动回放时按 `adapter-contract.md` 增加适配能力，不把示例或开发者测试结果当成业务事实。
