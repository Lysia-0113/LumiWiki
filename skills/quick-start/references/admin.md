# 后台任务参考

核心行为约束在 SKILL.md；这里给出工具选择和规划示例，不包含目标系统事实。

## 观察策略

- 页面先看 regions、tables、alerts 和 focus。活动 dialog/alertdialog/listbox 会优先返回，避免被大表格淹没；背景区可通过 regions 重新 inspect。
- 表格概览仅说明当前 DOM 的 renderedRows；browser_table(ref, contains=唯一标识) 返回列、行和行内控件。matched=0 只能证明当前已渲染范围没有匹配。
- 同名按钮依赖 row.ref、row.text 和 path 区分。需要详情时 inspect 该行，不能拿另一行的 ref 操作。
- 大表格默认截取前10行。用 offset 分段查看当前 DOM，用页面分页改变数据范围；虚拟列表用目标区域 ref 滚动后重读。分页、筛选和滚动是三种不同操作。
- 字段元数据提供 required/readOnly/invalid/description/placeholder。它们说明当前 UI，不能代替 Wiki 中的业务规则和真实错误验证。
- 未观察表单前，业务字段名不能被猜成某种控件角色。契约使用 `{label:"审批结果"}` 配 `selected_label_equals`、`texts:["通过"]`，表示选中业务标签，不依赖它是下拉还是单选；文本字段使用 `{label:"审批意见"}` 配 `value_equals`。输入框当前值不能用 text_equals 检查，select 含有“通过”这个选项也不代表已选中。

## 契约示例

“审批一张采购单”可以组织为：

1. 前置条件：当前有审批权限，目标唯一单号处于待审批状态。
2. 检查点一：在正确列表、筛选范围内定位同一单号，核对申请人和当前状态；截图。
3. 检查点二：打开该行抽屉，核对只读单号、审批选项和意见字段值；截图。
4. 提交：按当前测试授权完成确认；发生校验错误则核对错误，不当成成功路径。
5. 最终结果：回到列表或重新加载，核对同一单号的新状态及关键字段；验证、截图。

不要把示例的菜单和状态直接用于其他系统。数据种子、SSO 或后端断言只有宿主注册后才能使用；无法准备时 blocked。

## 文档标准

跨页面结果按 outcomeIds 分组执行 quick_start_verify。例如先在列表验证状态并截图，再进入日志页验证唯一记录并截图；不要要求两页同时可见。每组都必须留在证据归档中，用户文档只挑关键截图，不能把只通过一组称为完成。新的同站写请求会撤销当前场景的所有结果组；中间步骤保留为历史操作证据。

表格条件示例：`{"id":"status","description":"同一单号状态正确","target":{"role":"table","name":"采购单列表"},"assertion":"row_fields","rowKey":{"column":"单号","value":"PO-012"},"fields":[{"column":"状态","value":"已通过"}]}`。宿主要求唯一匹配行，并按列精确比较；“未通过”不会匹配“已通过”，其他行的数据也不能混用。列名须来自实际表格。未来整行尚未出现时，不拼接 role=row 的完整名称。

读者应能明确：入口的完整层级、要选哪条记录、筛选如何影响结果、哪些字段依赖其他选择、提交影响什么、去哪里核对、失败怎样恢复。归档截图分别关联中间检查点和最终结果；用户文档可以只展示关键截图，但不能省略实际核验与归档。

后台默认 profile=admin；成功场景至少2个检查点，空态/错误/权限至少1个。工具强制顺序、检查结果和图片覆盖；契约是否准确描述业务仍需复核。验证脚本和测试实现不属于模型上下文。
